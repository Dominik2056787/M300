## Was habe ich diese Woche gemacht?

Ich habe einen neuen, privaten Azure-for-Students-Account erstellt und darauf über Terraform eine komplette Infrastruktur aufgebaut: Resource Group, Virtual Network, Subnet, Public IP, Network Security Group und eine Linux-VM. Auf dieser neuen Azure-VM habe ich anschliessend Docker, kubectl, Minikube und Helm installiert, mein GitHub-Repository geklont und die komplette Applikation (Backend, Frontend, Kubernetes Secret) neu deployed. Zusätzlich habe ich das Frontend komplett neu gestaltet (moderneres "Matchday"-Design) und einen Autostart-Service eingerichtet, der die Applikation automatisch startet, sobald eine Instanz hochfährt.

## Was habe ich gelernt?

Azure-Subscriptions benötigen für neue Ressourcentypen (z. B. Netzwerk, Compute) eine einmalige Provider-Registrierung, bevor Terraform diese erstellen kann – das gibt es bei AWS in dieser Form nicht. Ich habe ausserdem gelernt, dass eine Cloud-zu-Cloud-Migration in der Praxis kein direktes Kopieren eines Server-Abbilds ist, sondern eine Re-Deployment-Migration: Die Infrastruktur wird über Infrastructure-as-Code neu provisioniert, während Code, Container-Images und Konfiguration unverändert aus der Versionskontrolle übernommen werden. Zusätzlich habe ich gelernt, dass Minikube Docker-Images anhand ihres Tags cached, weshalb bei jeder Code-Änderung ein neuer, eindeutiger Tag verwendet werden muss, damit die Änderung wirklich übernommen wird.

## Was war schwierig?

Der ursprüngliche Azure-for-Students-Account über die TBZ-E-Mail-Adresse war durch eine Tenant-Policy blockiert, die praktisch jede Ressourcenerstellung verhinderte – unabhängig von Region oder Ressourcentyp. Beim Aufbau der neuen, privaten Azure-Umgebung traten zusätzlich neue Fehler durch fehlende Provider-Registrierungen auf. Nach dem Deployment auf der neuen VM zeigte das Frontend zunächst weiterhin das alte Design, da Minikube das Docker-Image gecacht hatte. Anschliessend blieb die Datentabelle leer, weil das über GitHub geklonte Backend eine ältere Codeversion ohne Datenaufbereitung und mit falschem Parameternamen enthielt.

## Wie habe ich es gelöst?

Für die Tenant-Policy habe ich einen neuen, privaten Azure-for-Students-Account mit persönlicher E-Mail-Adresse erstellt. Die fehlenden Provider wurden gezielt über `az provider register` nachregistriert. Das Image-Caching-Problem habe ich durch konsequente Verwendung neuer Image-Tags bei jeder Änderung gelöst. Das Backend habe ich direkt auf der Azure-VM korrigiert, sodass es sowohl den Parameter `competition` als auch `liga` akzeptiert und die API-Antwort korrekt in ein flaches Array umwandelt.

## Zielerreichung

Die Applikation läuft nun vollständig und eigenständig auf Azure (VM, Netzwerk, Storage über Terraform provisioniert), erreichbar über eine eigene öffentliche IP mit Live-Daten von football-data.org. Damit ist die geforderte vollständige Multi-Cloud-Migration erfolgreich umgesetzt.
